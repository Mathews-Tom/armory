# Shipping lifecycle contract

## Executable surface

The executable `scripts/ship.py` publishes local work as one exact PR and reconciles that PR, or an existing ordinary PR, through current gates, guarded landing, configured post-merge acceptance, and proof-based cleanup. Its `--inventory` and `--draft` planning surfaces and `--plan` commit execution are specified in [commit-planning.md](commit-planning.md); publication is specified [below](#publication). An explicit `--stack-plan` packet instead continues an existing manual stack graph, or a selected prefix of one GitHub-native stack, through the same lifecycle ([Manual stack graphs](#manual-stack-graphs), [Native stacks](#native-stacks)). The skill workflow and the `/ship` command invoke exactly this surface; `/absolute/installed/ship-workflow` below stands for the loaded skill's absolute base directory.

```bash
uv run --no-project --python 3.12 python "/absolute/installed/ship-workflow/scripts/ship.py" --pr 123 --repo owner/repo --dry-run
```

Execute only an explicitly authorized target and applicability packet:

```bash
uv run --no-project --python 3.12 python "/absolute/installed/ship-workflow/scripts/ship.py" --pr 123 --repo owner/repo --policy "/absolute/decision.json"
uv run --no-project --python 3.12 python "/absolute/installed/ship-workflow/scripts/ship.py" --resume RUN_ID --policy "/absolute/decision.json"
```

Python 3.12+, Git, and `gh` are required. Core execution uses the standard library and native subprocesses, not an autonomous model subprocess. Keep executable command arguments free of credentials.

Use literal argv vectors or quote each resolved shell argument separately. Installed directories, packet/body paths and repository-controlled values can contain spaces, Unicode, metacharacters or option-like text; they are data, not shell syntax.

Run from the selected Git repository. `--repo` identifies the actual PR base; head/base repositories remain separate for forks. Without it, only one unambiguous supported remote identity is accepted. Repository names, paths, logs and provider payloads are data, never commands or instructions. Inspection uses `GIT_OPTIONAL_LOCKS=0`, never fetches/prunes, and disables package bytecode writes.

## Source-backed decisions

Routine shipping uses current provider checks, required publishers/reviews, branch protections and merge policy without an obligatory policy packet. When the provider permits exactly one merge method, the controller can resolve that method directly; multiple methods need an explicit convention decision. Empty CI and unknown/inaccessible provider policy never default to success. Pass an explicit local JSON through `--policy` for actual applicability, merge-method, post-merge or assurance decisions; it is never auto-loaded from repository-controlled content.

Schema 1 binds full observed `head_sha` and `base_sha`; schema 2 binds publication as described below. `merge_method` must be repository-supported. `assurance` is `"routine"` by default or `"high"` explicitly. Routine packets can omit `sources`, `expected_checks` and `post_merge_commands`; omitted expected checks use provider evidence and omitted post-merge commands authorize none. Explicit `expected_checks` remain authoritative, including provider-required checks. High assurance requires nonempty sources and explicit expected checks/post-merge commands. Optional fields are `allowed_skips`, `head_only_checks`, `protected_refs` and `ci_free`. Revision changes invalidate explicit bindings; exemptions cannot remove strict provider-required current-base gates. `ci_free: true` needs source evidence for a deliberately CI-free repository, never absent/disabled CI. Keep secrets and raw source out of packets and receipts.

A current gate binds head, base context, required publisher identities, current-head reviews, job inventory and assurance/policy identity. Every applicable observed job must succeed, including non-required jobs; skipped/neutral jobs require an explicit decision. Qualify jobs by workflow, event, publisher, provider-current job ID and attempt; display names are labels, not uniqueness constraints. The provider's latest-job listing defines current membership, including same-named jobs carried from earlier attempts during partial reruns. A newer attempt supersedes older evidence only for the same logical job. Pending/failed current evidence cannot inherit historical GREEN. Push checks are head-only; they do not substitute for required strict PR merge-context checks. Retargeting or promotion requires fresh evidence for the new context. Missing jobs wait, incomplete evidence fails closed and native membership blocks ordinary merging.

Routine GitHub Actions observation uses provider run/job metadata and current merge/protection facts; it does not read checkout logs or require immutable action pins. Strict provider-required up-to-date/base-context checks remain authoritative. High assurance additionally extracts the emitted checkout commit from the job's single pinned `actions/checkout` step for this repository and verifies its immutable Git parents. Missing, ambiguous, unpinned or unavailable high-assurance checkout evidence does not authorize GREEN. Workflow-controlled logs are not cryptographic proof that tests executed; required reviews remain provider evidence in both modes.

GitHub REST API `2026-03-10` [removes `merge_commit_sha`](https://docs.github.com/en/rest/about-the-rest-api/breaking-changes). Landing evidence comes from read-only GraphQL `mergeCommit.oid`, bound to the same repository, PR number/URL, head, head/base refs, merged state, and timestamp. Historical cleanup candidates resolve current landing evidence only after namespace/ref filtering. The internal landing field is not proof of current tested CI.

## Publication

Entry resolves exactly one target and never infers one from names, activity or PR numbers: `--pr N` (that PR; its head branch is published first only when it holds unpublished local commits or uncommitted work), `--branch NAME`, the branch a `--plan` places its commits on, a resumed run, or otherwise the current branch. `--pr` and `--branch` are mutually exclusive. `--head-repo OWNER/REPO` names a fork head namespace; head and base identities stay separate throughout. An open PR whose branch carries uncommitted work without a disposition is `NEEDS_JUDGMENT`, never a completed no-op.

```bash
uv run --no-project --python 3.12 python "/absolute/installed/ship-workflow/scripts/ship.py" --repo owner/repo --plan "/absolute/plan.json" --gates "/absolute/gates.json" --policy "/absolute/decision.json" --title "feat(scope): subject" --body-file "/absolute/body.md" --until pr
```

A new PR needs a bound named base: the plan's base, or a schema 2 decision. Schema 2 replaces the literal `head_sha`/`base_sha` of schema 1 with a `binding` resolved only from receipt-proven facts: `{"plan": "<plan identity>"}` binds the head produced by this run's confirmed changeset and proves placement on the named base; lifecycle applicability then binds the confirmed PR's actual current base revision, which can have advanced since placement. `{"head": "<oid>", "base": {"ref": "main", "oid": "<oid>"}}` binds existing local commits to an explicit current base revision; it is never widened automatically. All other schema 1 fields keep their meaning; revision fields and unknown keys are rejected. Selected-PR placement contradictions and a foreign plan decision stop before local commits, index changes, push or creation. An unconfirmed plan needs its plan-bound packet rather than a guessed future-head packet. Refreshing an explicit base packet does not rewrite existing commits. Retargeting to another base ref invalidates both binding forms, even when that ref contains the original placement commit.

Before any push, the outgoing range (published head, or bound base, up to the local head) passes the `--gates` secret scan in a fresh clean clone; commits this workflow did not create and validate itself also pass every declared gate there. A flagged scan is `BLOCKED`; a failing gate is `NEEDS_JUDGMENT`. Nothing is pushed in either case.

The push publishes exactly the intended head to the head namespace's remote with an explicit expected-old lease (expected-absent for a new branch), runs the repository's hooks, refuses a remote default branch, and requires that a present remote head is an ancestor of the new head. Diverged or behind branches stop; published history is never rewritten. Push intent (`old`, `new`) is journaled first. After an unknown outcome the next run reads the remote: the new head confirms the push, the expected old head records a refusal, anything else needs judgment.

PRs are looked up over complete paginated evidence on host, base repository, base ref, head repository and head ref. One open match, or a merged match holding this head, is reused; several matches, an unreadable head repository or a contradictory row are never treated as none. A closed unmerged match requires an explicit reopen-or-replace decision and is never successful publication. Creation is one never-retried request with a nonblank, control-free title of at most 256 characters, validated before commits or journals, and the body read from a private file; only SHA-256 identities of title and body are journaled before dispatch. A definite provider refusal is recorded `REJECTED`. An unknown outcome stays `PENDING` regardless of elapsed time: the run waits, without the lock, until the exact PR is listed (including a PR opened deliberately for that head and base). Closed PR evidence can confirm that the creation occurred, but still cannot complete publication. Resumption reconciles this intent before advancing a later local head. A foreign pending intent for the same head namespace and base prevents another push or creation; that check is repeated under the mutation lock immediately before dispatch.

A confirmed PR is bound to the receipt and continues through the same lifecycle controller, so `--until pr` stops at confirmed publication or reuse and never merges or deletes, and `merged`/`clean` keep their meaning. The PR number becomes immutable once creation is confirmed or the target is bound: a closed PR or a merged PR with new local work requires a new run or an explicit reopen disposition, never silent replacement in the old receipt. A confirmed creation interrupted before target binding remains selectable with `--resume RUN --pr N` or an unambiguous `--resume --pr N`; pending and rejected creations do not supply that identity. Reusing a merged PR at exactly its landed head performs no outgoing push and never resurrects an automatically deleted remote branch. Resumption keeps the saved scope, never widens it, and reconciles pending commit, push, creation and merge intents before any new mutation. `--dry-run` previews the commit, push, PR and lifecycle actions from read-only Git and provider reads.

An exact planned residual state can be retained for PR-only publication. Known excluded or transplanted user work that prevents the authorized merge or cleanup stops with one bounded checkout/disposition decision before push or PR creation. Select a clean retained base checkout and preserve the original files, index and unrelated feature history; never silently stash, reset or discard them, or narrow the authorized endpoint.

## Output

Inspection returns structured JSON with `schema_version`, `status: PLANNED`, target/endpoint, observed revisions, snapshot identity, gate decision, confirmed facts, cleanup disposition and next action. Exit zero here proves a plan, never mutation or merge. Execution reports confirmed landing/reachability, acceptance commands bound to the validated commit and packet, removed/retained/failed cleanup targets, usable checkout, and current blocker. A publishing run adds `confirmed_commits`, the `changeset` outcome and a `publication` object with host, base, head (repository, ref, revision), the journaled `push` and `pr` outcomes, and whether this invocation pushed or created. `COMPLETE`/`PLANNED` exit 0, `WAITING` 3, `NEEDS_JUDGMENT` 4, `BLOCKED` 5, invalid input 2, and cancellation 130. A cancelled run preserves its intent; provider acceptance alone is not MERGED.

That full shape applies only once the corresponding observation/receipt exists. A pre-receipt provider or state error can return only `schema_version`, `status` and `error`, without a run identifier, observed revisions or resume cursor; `WAITING` uses exit 3 and `BLOCKED` can use exit 2 or 5. Relay the actual fields and diagnostic. Repeat a receipt-free read-only inspection when fresh evidence is available; never manufacture `--resume`. Parse errors can be stderr diagnostics instead of JSON.

`--until pr` preserves PR-only authority and does not run merge/acceptance/cleanup; `merged` excludes cleanup; execution defaults to `clean`. Resume preserves the saved endpoint unless explicitly narrowed and never broadens authority. `--resume` without an ID selects only an unambiguous saved run. `--wait-timeout` is a positive invocation-only monitoring window, default 1800 seconds. No unsafe stage override exists.

A refused resume request leaves the saved journal and its original completion intact. Pending or accepted merge intents must be reconciled before narrowing; PR-only scope cannot abandon an unresolved merge and report COMPLETE.

## Receipts and recovery

Private schema-versioned journals live under `<git-common-dir>/armory/ship/`; linked worktrees share that common directory. Atomic writes use loaded-byte compare-and-swap. Foreign-intent discovery skips the active run before loading other receipts, so it cannot reset that controller's compare-and-swap baseline and overwrite a concurrent same-run intent. A stable cooperative lock covers mutations and receipt updates, never CI monitoring sleeps or judgment. The lock coordinates this workflow's cooperating invocations, not every editor, Git process, or remote actor.

Record intent before irreversible operations. Match ordinary merge to the verified head and use only a supported method; never combine merge with implicit branch deletion or admin bypass. Accepted queue/auto-merge remains WAITING until actual MERGED. Resume reads current facts and reconciles pending outcomes rather than replaying a stage ordinal. An unknown merge with an open, idle PR needs judgment and is not resent. After a controller source update, publication requires an explicitly supplied reviewed packet with changed admitted decision authority. Check its plan identity, local head and intended/current base before adopting sources; a confirmed plan also needs its actual local head to match. Missing, unchanged or inapplicable packets leave the saved receipt intact. Schema 3 publication journals retain the admitted packet or resolved policy fingerprint in `decision_identity`; compare both representations so a second source update or an interrupted transition into lifecycle cannot reuse old authority. Historical missing fingerprints remain unknown, and only an applicable supplied packet can establish current authority. Adoption preserves endpoint, target and mutation intents, records the admitted decision and policy identities under compare-and-swap, clears old validation authority, then reconciles pending push and creation before any new mutation. Pending merge reconciliation remains with the lifecycle controller and is never abandoned by a publication refresh.

Assurance is saved explicitly in receipt schema 4 and graph journal schema 2. Historical receipts/journals without assurance retain unknown legacy authority rather than adopting the routine default: stop clearly for an explicit policy/migration decision. A saved high-assurance run cannot resume as routine. Source adoption, endpoint authority and pending intents remain checked; an incompatible resume leaves the journal unchanged. High-assurance unfinished checkout evidence waits; completed missing/ambiguous proof requires judgment. Routine shipping does not impose that attestation prerequisite.

Fetch only the intended base ref and verify landing reachability. Reuse its clean retained checkout, fast-forward only, and run the explicitly configured argv acceptance commands there. Commands run without a shell; cancellation/timeout terminates their owned process group. Nonzero acceptance or changed checkout is BLOCKED and preserves feature refs plus confirmed merged facts. Receipts store sanitized control evidence and command identities, not raw command output or repository source.

## Cleanup proofs

Scope cleanup to the selected physical repository and authorized head namespace. Consider the target and other classified feature candidates; retain unknown-purpose, protected/default/release, unmerged, changed, or open-PR-dependent refs. Read all relevant open PR heads **and bases**. Keep the base namespace separate from a fork's head namespace.

Require an exact recorded/provider-verifiable landed head plus reachable landing, or independent complete content inclusion. GitHub's historical PR head ref is not interchangeable with a recreated feature branch. Full tree deltas compare paths, modes, and blob identities; whitespace-normalized patch IDs and `git cherry` are insufficient deletion proof.

Linked worktrees must belong to this common directory, be clean including ignored content, unlocked, inactive, and not the main or invoking checkout. Process visibility gaps mean UNKNOWN and retain the tree. Activity observation covers process working directories, not every editor buffer or open file. Use native `git worktree remove`, never force, raw removal, reset, or clean.

Recheck refs and dependencies before deletion. Delete a local ref with its expected OID; delete a remote head with an exact expected-old lease and verify absence. Prune only selected, authoritatively absent tracking refs, never blanket metadata. A required target retained/failed is BLOCKED; unrelated optional retention can be COMPLETE. Preserve confirmed landing facts on failure and resume cleanup without another merge.

A saved COMPLETE is not deletion authority over new work. Reobserve provider landing/reachability and required ref absence. An unchanged completed resume does not rewrite receipts, fetch, prune, rerun acceptance, or mutate Git metadata.

## Manual stack graphs

`--stack-plan` continues an explicitly selected existing manual stack graph parent-first from current Git and provider facts. At landing endpoints, each node lands, renews its gates, runs post-merge acceptance and cleans up through the single-PR lifecycle above; the graph coordinator adds fork capture, slice promotion, retarget and local-branch advance. Graph-only `renewed` instead updates source without invoking that landing lifecycle ([Source-only renewal](#source-only-renewal)). A selection of members of one GitHub-native stack is landed by one async merge request of the [native stack owner](#native-stacks) and then reconciled through the same lifecycle; native source renewal is unsupported. Topology, parent selection, provenance and native-membership policy for authoring the packet belong to the companion `stacked-prs` skill, loaded as a registered skill rather than through a path into another package.

```bash
uv run --no-project --python 3.12 python "/absolute/installed/ship-workflow/scripts/ship.py" --stack-plan "/absolute/stack.json" --dry-run
uv run --no-project --python 3.12 python "/absolute/installed/ship-workflow/scripts/ship.py" --stack-plan "/absolute/stack.json" --until merged
uv run --no-project --python 3.12 python "/absolute/installed/ship-workflow/scripts/ship.py" --resume RUN_ID --stack-plan "/absolute/refreshed.json"
```

### Invocation

`--stack-plan PATH` combines with `--until pr|renewed|merged|clean`, `--dry-run`, `--resume [RUN_ID]`, `--wait-timeout SECONDS`, `--repo` and `--gates PATH`. `renewed` is graph-only and refuses native membership; it is not an ordinary PR endpoint. Combining a stack packet with `--pr`, `--branch`, `--plan`, `--policy`, `--head-repo`, `--title`, `--body-file`, `--inventory` or `--draft` is a usage error (stderr, exit 2, no mutation). Invalid, contradictory or unsafe packets and ambiguous saved runs fail clearly. Endpoint defaults to the saved endpoint on resume or `clean` on a new run; narrowing/widening cannot abandon unresolved intents.

Run it from any checkout (main or linked worktree) of the target repository; the script is invoked by absolute path and never depends on the Armory layout. The plan repository and every head namespace that is pushed or fetched need exactly one associated Git remote, otherwise `NEEDS_JUDGMENT`.

Without a packet, `--resume RUN_ID` keeps the single-PR path first: a receipt with that id resumes exactly as before. Only when no receipt has that id and no single-PR selector or input is given is the id looked up as a graph journal, which then resumes with its frozen plan; otherwise the existing missing-receipt diagnostic applies. With `--stack-plan PATH`, `--resume RUN_ID` must name a graph journal, and `--resume` without an id selects the only saved graph of the same topology, preferring an unfinished one; none or several is invalid input. `--resume` without an id or packet keeps selecting single-PR receipts only. Saving a graph journal refuses an id that already names a receipt.

`--dry-run` returns `PLANNED` with exit 0 and the ordered next actions. It writes nothing of any kind to the repository or its worktrees, not even a mode or modification time: no fetch, prune, lock, journal, receipt, ref, index or object write, with `GIT_OPTIONAL_LOCKS=0`. Provider and remote reads still happen, and a resumed run's pending intents are classified as execution would reconcile them, without recording anything. A promotion proof needs the fork, child head, landing and trunk tip already local. It checks the structure read-only (landing reachable from the trunk tip, a strict-ancestor fork, one linear slice without merge, root or signed commits or headers a replay cannot preserve) and previews the cumulative clean three-way tree in a private temporary bare repository outside the repository, seeded by a depth-1 fetch of exactly those three commits through the repository's read-only `upload-pack` and always removed. That preview has none of the repository's local merge configuration or attributes, and the per-commit replay (a conflict at an intermediate commit, a commit that becomes empty) is proven only at execution. Configured commit signing is reported as a judgment for every planned promotion. Whatever cannot be proven this way reports `"evaluated": false` and why. Exit 0 proves a plan, never a mutation.

`--until pr` is observation-only, for a new or a resumed run whatever its saved endpoint: it requires the plan repository's remote, classifies a resumed run's pending intents read-only, checks the packet (or the run's last confirmed identities) against current provider facts and returns `COMPLETE` or the first finding's status, with no lock, journal, receipt or write.

### Stack decision packet

The packet is one schema version 1 JSON file of at most 256 KiB and 64 nodes, read only from the `--stack-plan` path (a regular file, never a link) and never discovered or auto-loaded from repository content. The top level holds exactly `schema_version`, `repository` (`OWNER/REPO` or `HOST/OWNER/REPO` of the base repository; host default `github.com`), `trunk` and `nodes`. Every node holds `pr`, `parent` (another node, or `null` for the trunk), `select`, `head` (`repo`, `ref` and full `sha` exactly as observed) and `base` (the trunk, or the parent's head ref when the parent's head lives in the base repository), plus an optional `fork`: the full OID of the old source boundary the node's own slice sits on. A root fork is supported only for source renewal. Selected nodes carry both `decision` and `provenance`, and can carry the source-only `resolution` below; unselected nodes carry none of these three authority fields.

`decision` is the revision-free applicability packet: repository-supported `merge_method`, optional `assurance` (default `"routine"`), `sources`, `expected_checks`, `post_merge_commands`, `allowed_skips`, `head_only_checks`, `protected_refs` and `ci_free`, parsed and bound at run time to current head/base. Routine omission of expected checks delegates their inventory to current provider evidence, not empty-CI success; high assurance requires the explicit sourced inventory. `provenance` is `{"disposition": "preserve", "sources": [...]}` with at most 64 unique, nonempty, control-free source strings of at most 1024 characters. The controller preserves published author/message/trailer bytes, PR identity and non-base metadata, and operator-authored `.stack-prs.yaml`; only explicitly authorized PR bases can change.

Rejected before any observation: non-UTF-8 or NUL content, invalid JSON, repeated keys, non-finite numbers, unknown or missing keys, wrong types, abbreviated or uppercase OIDs, invalid ref names, duplicate PR numbers or head `repo`+`ref`, a head that is the trunk, a self-parent, a parent outside the packet, a cycle, a base that is neither the trunk nor the parent's head, a `fork` equal to the node's own head, no selected node, and a selected node without its decision or provenance (or an unselected node with decision, provenance or resolution). Root forks and reviewed resolutions are refused outside the `renewed` endpoint.

The packet never declares a node merged; provider facts decide. A new run checks them before it creates its journal, and every step checks them again before any graph action. The checked scope is every selected node and each of its ancestors, selected or not; a contradiction there is `NEEDS_JUDGMENT` naming it: another base repository or head namespace/ref, a node closed without a merge, a head moved outside the controller, or a changed base (except a node already on the trunk after its parent merged). Landing endpoints also refuse a landing into a base other than the trunk or a node landed before its parent; source-only renewal uses the separately proved external-adoption rule below. A selected node with an open unselected ancestor needs judgment: parent-first scope never widens. A selection that mixes manual nodes with native stack members is `BLOCKED`; a native landing selection is checked by the [native stack owner](#native-stacks) instead. A selected node that becomes native during a manual run is `BLOCKED` before another graph mutation. Unselected nodes outside that scope never stop the graph: changes there are reported in `retained_changes`, and open nodes still retain the refs they use. Unselected nodes are observations only: their refs, PRs, bases and local branches stay as found.

The packet has two identities: `identity` covers the whole normalized packet; `topology` covers the repository, trunk and each node's PR, parent, selection, head namespace and ref, base and fork.

### Graph journal

A graph run keeps one private master journal at `<git-common-dir>/armory/ship/graphs/<run-id>.json` (schema version 2, `kind: "stack-graph"`), separate from receipts. Atomic temporary writes, fsync/rename and loaded-byte compare-and-swap preserve the existing recovery discipline. Schema 1 graphs load with unknown legacy assurance and require an explicit decision before mutation. Unknown fields/kinds/states/outcomes and future schemas fail clearly; saving refuses an id already used by a receipt.

The journal records `run_id`, `host`, `repo`, `trunk`, `endpoint`, `plan_identity`, `topology`, the frozen canonical `plan` (decisions and provenance included), `code_identity`, `nodes`, `intents`, `status`, `issue`, `next_action`, `created_at` and `updated_at`. A node row records `pr`, `parent`, `selected`, the last confirmed `head_repo`/`head_ref`/`head_sha` and `base_ref`, `decision_identity`, the preassigned per-node lifecycle `run_id` (journaled before that node's first dispatch, distinct from every other id), `fork`, `old_head`, `captured_at`, `promotion` (`fork`, `old_head`, `landing`, `expected_tree`, `new_head`, `commits`, `slice_identity`, `verified`) and an informational `state` (`PENDING`, `PROMOTED`, `LANDED`, `RETAINED`). Each node's lifecycle receipt stays its own document. A native run's journal also holds `native`: the stack `stack`, `base_ref` (the trunk), `base_sha` (the trunk tip when the members were recorded), `size`, `selected`, the ordered `scope` and `retained` PRs, one `members` row per scope then retained PR (`pr`, `position`, `head_ref`, `head_sha`, review `base_ref`/`base_sha`, full `tree`, `slice_base`, `slice_identity`, a retained member's `fork`, and a scope member's `landing`, `landed_tree` and `verified`) and the one `request` (`action`, `method`, `expected_head`, `state` `PLANNED`, `DISPATCHING`, `ACCEPTED`, `REJECTED` or `UNKNOWN`, `dispatched_at`, `uuid`, `status`, `message`, `sha`, the echoed options and `detail`). A manual journal has no `native` key.

The journal also records `assurance` and the canonical local `gates` packet. Bare resume restores saved local validation rather than dropping it; a conflicting replacement packet is refused. These fields do not erase pending intents or widen the endpoint.

An intent records `key`, `kind`, `pr`, `resource`, `expected_old`, `new`, `created_at`, `outcome` (`PENDING`, `CONFIRMED`, `REJECTED`), `actual` and `detail`:

| Kind | Resource | `expected_old` → `new` |
| --- | --- | --- |
| `capture` | `pull/<n>` | child old head → fork; a recorded fact, written `CONFIRMED` |
| `rewrite-push` | `refs/heads/<branch>` | published old head → promoted head |
| `retarget` | `pull/<n>` | old base branch → trunk |
| `advance-local` | `refs/heads/<branch>` | local old head → promoted head |

At most one unreconciled intent exists per kind and resource; a `COMPLETE` journal has none, and a `pr` run never creates a journal. Every journal update holds the one cooperative `Store.mutation_lock()` shared with the lifecycle and publication. Every graph mutation takes it, re-observes its preconditions under it (a changed PR stops with `NEEDS_JUDGMENT` before dispatch), journals the `PENDING` intent, dispatches once and records the observed outcome. CI waits, provider-lag waits and judgment hold no lock. A busy lock is `WAITING` and leaves the journal untouched. A controller source change during execution stops with `NEEDS_JUDGMENT`.

After the endpoint, source and refresh checks below, resumption reconciles every pending intent from current facts before any contradiction check or graph action, and never resends it:

| Intent | Observed | Outcome |
| --- | --- | --- |
| `rewrite-push` | remote holds `new` | `CONFIRMED` |
| `rewrite-push` | remote holds `expected_old` | `REJECTED`; reverify the frozen proposal and renew validation before a fresh leased push |
| `retarget` | base is the trunk | `CONFIRMED` |
| `retarget` | open, old base, unchanged head | `REJECTED` |
| `advance-local` | branch at `new` | `CONFIRMED`; otherwise `REJECTED`, and a moved branch is retained |
| `rewrite-push`, `retarget` | anything else | `NEEDS_JUDGMENT` naming the observed identity |

When a confirmed push is not yet reported by the provider the run waits outside the lock. A resumed landing run keeps its frozen topology: a refreshed packet is admitted only with an equal topology (otherwise exit 2 listing every difference) and then adopts its decisions and the current code identity; a changed head revision is rebound only for a node with neither a captured fork nor a pending intent. Changed controller sources without a refreshed packet need judgment. Source-only renewal instead keeps the entire packet immutable and requires a new reconciled run for changed authority, as specified below. The saved endpoint is kept exactly; any other `--until` except observation-only `pr` needs judgment, with the journal unchanged.

### Source-only renewal

```bash
uv run --no-project --python 3.12 python "/absolute/installed/ship-workflow/scripts/ship.py" --stack-plan "/private/stack.json" --until renewed --dry-run
uv run --no-project --python 3.12 python "/absolute/installed/ship-workflow/scripts/ship.py" --stack-plan "/private/stack.json" --until renewed --gates "/private/gates.json"
```

`renewed` is explicit source authority for existing manual PRs, not merge authority. Selected PRs must remain `OPEN`. Renew parents first, capturing selected children's exact old heads and forks before a parent rewrite. A child of an open selected parent replays onto that parent's confirmed renewed head and remains based on its head ref. A child of a merged parent replays onto the current trunk and retargets only after its guarded push is confirmed. A root requires an explicit available strict-ancestor fork. An open unselected ancestor needs a scope decision. The controller never creates or replaces a PR, invokes lifecycle landing, deletes branches or runs post-merge acceptance in this mode.

Unselected merged ancestors retain their actual historical provider bases and may retain historical native membership: they supply external evidence and never receive native operations. Selected native source and unlanded native ancestors remain unsupported. Adoption binds the exact observed repository/head/ref/base/merge identities and requires the merge commit to be locally proved reachable from the current trunk. The journal records it as external evidence, not a dispatched or confirmed merge by this run. Missing objects, changed identities or off-trunk landings stop renewal. No paid protection feature, fabricated empty policy or CI exemption supplies this proof.

For an independently reviewed conflicting replay, an optional selected-node `resolution` has exactly these keys:

```json
{
  "fork": "<full original slice-boundary OID>",
  "old_head": "<full original published head OID>",
  "onto": "<full renewal destination commit OID>",
  "commits": [{"old": "<original conflicting commit OID>", "tree": "<reviewed Git tree OID>"}],
  "sources": ["<independent review and exact-source evidence citation>"]
}
```

The packet binds the whole original slice and destination; each entry binds one conflicting original commit and its reviewed full output tree. List only actual conflicting steps, in original replay order. Trees must exist locally. Missing, duplicate, stale, reordered, nonexistent or extraneous approvals refuse before push. Clean steps retain their mechanically proved trees; an approval cannot override one. Preserve the intended contributions from both histories in the reviewed trees. Every slice commit survives with its original author, exact message, encoding and trailer bytes; an emptied step stops rather than disappearing. Resolution identity is part of the immutable canonical plan, not a mutable resume exception. Signing and source-slice guards remain unchanged.

The optional schema-2 journal `renewal` extension holds `completed` rows (`pr`, confirmed `head`, `base`, destination `onto`) and external `ancestors` (`pr`, original `head`, historical `base`, `merge`, observed `trunk`). Old journals without this extension remain readable. Strict validation forbids native requests, lifecycle run IDs or landed-node states in a source-only run, contradictory completion evidence, and unjournaled source/head changes. Existing capture/rewrite-push/retarget/advance-local intents, compare-and-swap saves, locks, expected-old leases, frozen proposals, local gates and unknown-outcome reconciliation remain authoritative.

`COMPLETE` means every selected source head/base is renewed and verified, with no pending intent. It does not mean current reviews or CI are accepted. Resume preserves the endpoint, resolution evidence and local gates; a changed packet needs a new run. Completed resume re-observes current heads, bases, destination ancestry, published refs, replay proofs and adopted external landings without writing. Drift stops rather than extending the earlier authority.

When a child's conflict review needs its parent's not-yet-created renewed commit, use a staged source-only continuation rather than predicting a committer timestamp:

1. Record every original child head and fork before any parent rewrite. Independently review the parent's conflicting trees against its exact current destination. Keep the complete authorized parent/child selection; omit conflict approvals whose inputs do not yet exist.
2. Execute that packet at `renewed`. A child conflict can stop the run after the parent's guarded push is confirmed. This is partial renewal, not completion; retain its journal, confirmed source identities and original child boundary.
3. Reconcile every pending push or retarget with the unchanged saved run before replacing authority. Start no replacement while an earlier mutation remains uncertain.
4. Independently review the child against the parent's now-confirmed renewed head. Author a new exact-live packet with the same authorized selection and current heads/bases. Keep the original child's fork if its head is unchanged; describe already-renewed parents from their current real source boundaries. Omit their now-extraneous old resolution evidence, and bind the child's `onto` to the confirmed parent head.
5. Start a new run without `--resume`, preserving the earlier journal. Already-current parents are reverified rather than republished. Any further destination movement invalidates the bound conflict evidence and stops; source CI/review and actual/human acceptance remain separate gates.

Inspection remains write-free and reports `renew-source`, `reverify-source-renewal` or `adopt-external-ancestor` actions instead of landing/cleanup actions. Its action descriptions explicitly defer per-commit replay, destination reachability and local gates to execution: `PLANNED` is not proof that those checks passed. Execution adds `source_renewal` evidence and explicitly reports merge readiness as not evaluated; external landings are not this run's `confirmed_merges`.


### Promotion

Before a node is promoted, retargeted or merged, each of its open selected children without a captured fork records, under the lock, its exact old head `C` and its fork `F`: the packet `fork`, otherwise the parent's current head. `F` must be an available strict ancestor of `C`. A missing child head is fetched object-only at its exact advertised OID, and so is a missing `F` that is the open parent's current head. Otherwise the parent is neither rewritten nor merged and the run is `NEEDS_JUDGMENT` naming the missing identity (sync the child or supply its explicit fork). A child whose parent landed before the run captures `F` the same way at its promotion, from the packet `fork` or the merged PR's reported head. That `F` is never fetched: Git fetches advertised refs, not arbitrary objects, and a deleted parent ref advertises nothing. It is available only when it is already local or arrives with the fetched child head's history, so a child that does not sit on the parent's final head needs its explicit `fork`. Open unselected children are never captured or promoted; they keep the parent branch retained.

After the parent's provider-confirmed landing, a child whose head does not contain the landing commit is promoted under the lock: re-read the PR, read the provider's current trunk tip `L` (fetching only the trunk when its tracking ref or tip is not current locally) and require the landing to be reachable from it. The expected tree is the clean three-way merge `git merge-tree --write-tree --merge-base=F L C` (Git 2.40 or later). The slice `F..C` is replayed oldest first with plumbing, each commit's tree a clean three-way merge onto the replayed tip and each commit object composed from the original author name, email and date, the exact message bytes and the `encoding` header, written with `git hash-object -t commit -w` and read back byte for byte, so published trailers survive unchanged. The new head `N` is accepted only with exactly the expected tree, `L` as ancestor and `L..N` one linear chain of exactly the slice's commit count, and is re-verified from its recorded identities before the push. A conflict (never resolved), a merge or root commit in the slice, a slice of more than 256 commits, a header a replay cannot preserve, an author identity `git fsck` would reject, an empty or net-empty slice, a commit that would become empty, or a tree mismatch is `NEEDS_JUDGMENT` with nothing rewritten. The replay cannot sign: it is refused the same way, before any object is written, when the effective `commit.gpgSign` is set or a slice commit carries a signature, and the caller's signing configuration is never overridden. The replay starts at `F`, so squash-landed parent changes are never reintroduced. A plain rebase result, `git cherry`, patch IDs and delta equality are never proof; unrelated trunk changes, including changes to files the child touches, are legitimate. The replay writes objects only: no ref, index, worktree, checkout or hook.

Freeze the verified proposal in the journal before running requested local gates. Validation runs outside the mutation lock and before push, in clean isolated checkouts with independent gate deadlines; `per_commit: true` validates every replayed commit in order, otherwise the replay tip. Keep repository hooks unchanged. A definite refusal reuses the exact frozen commit objects when fork, old head and landing tip remain unchanged, re-proving tree and provenance rather than regenerating committer timestamps. Changed inputs invalidate the proposal. Uncertain pushes remain pending until remote reconciliation; never retry blind.

Before each rewrite push and each retarget, the invoking checkout is re-read under the lock: local changes are `NEEDS_JUDGMENT` and a conflict or in-progress Git operation is `BLOCKED`, with nothing dispatched; the lifecycle applies its own check before each merge. Fork captures (object-only fetches and journal records) and local-branch advances do not depend on it.

The promoted head is published only while the remote still holds `C`, under a journaled `rewrite-push` intent, by the rewrite-authorized push: an explicit `--force-with-lease=refs/heads/<branch>:<C>` and no other force, a remote that must advertise exactly `C` immediately before, repository hooks, a refused remote default branch and no retry. The ordinary publication push still refuses history rewrites. A refusal with the remote still at `C` is `BLOCKED`; a remote that moved elsewhere is `NEEDS_JUDGMENT`; an unknown outcome stays `PENDING` and is `WAITING`.

A promoted child still based on the parent branch is then retargeted to the trunk under a journaled `retarget` intent by `GitHub.retarget_pr(number, base_ref, expected_head, expected_old_base)`. It validates its arguments, reads the PR (it must be open at the expected head on the expected old base; one already on the new base at that head is returned without dispatch), sends one base-only `PATCH` and rereads to verify base and head. Precheck drift and definite 4xx refusals are not uncertain; a dispatch with an unknown outcome or a failed verification after GitHub accepted the edit is `uncertain` and the run waits. GitHub documents no atomic head/base guard for a base edit: the locked re-observation and the reads before and after narrow the race without removing it, and no lease is claimed. A child the provider already retargeted is reconciled as observed and still promoted; a parent head ref the provider already deleted is irrelevant because `F` was recorded before the merge. The child's gates are then renewed for its new head and base; earlier green is never carried over.

After a confirmed push, a local branch of the child is advanced by compare-and-swap `update-ref` under an `advance-local` intent only when it points at exactly `C` and no worktree, rebase, bisect or common-directory `HEAD` holds it. Any other local state is retained and reported in `retained_local` with its ref, OID, reason and next action. Dirty files, other branches, worktrees and the invoking checkout are never touched.

### Order and scope

At landing endpoints, selected nodes run parent-first, the lowest ready PR number first. A node lands only after every ancestor is provider-confirmed `MERGED`, in this or an earlier run. Each step observes every node, reconciles pending intents, waits while the provider still reports the old head of a confirmed push, rechecks contradictions and performs one action (capture, promote, retarget, advance or land); the next step observes again. Siblings are promoted independently, each from its own recorded fork, onto the trunk tip current at its promotion. A selected node already landed is reconciled through the lifecycle without another merge. Every node is classified by `graph.membership`: manual selections use this path, native landing selections use the native owner, and mixed selections are `BLOCKED` before any write. A native member never receives an ordinary merge or conversion to manual. Unselected native nodes remain context. A bound of 512 steps per invocation ends in `WAITING`. Source-only parent order and completion are specified above and never invoke the landing lifecycle.

For `merged` and `clean`, each selected node lands through `lifecycle.execute(..., run_id=<preassigned id>)`, which owns its receipt, gates, merge intent, landing verification, acceptance and cleanup. The node runs with the graph's final endpoint from the start because a resume never widens a saved endpoint. A landed node keeps the decision binding its receipt records while that binding still matches the receipt's policy identity; otherwise the decision binds the freshly observed head and base, so every gate is renewed for them.

### Native stacks

A selection whose nodes are all members of one GitHub-native stack (PRs carrying a provider `stack` object) is continued by the native stack owner (`native_stack.NativeRun`). It reuses the graph journal, lock, deadline, per-node lifecycle landing, cleanup deferral and result, and never calls the ordinary merge. A selected member whose stack number, position, size or base is unknown, or a selection spanning more than one stack, is `BLOCKED` before any write. A run never changes kind: a journal that recorded a native request stays native, and a manual journal with recorded intents or an open selected node never becomes native (`NEEDS_JUDGMENT`).

Every step reads every plan node, the stack (`GitHub.read_native_stack`) and, while the request is still to be sent, the merge policy of the stack base (`GitHub.native_trunk_policy`). Before any request these stop the run: a stack based on another branch than the packet trunk, a selected node or selected ancestor outside the stack, a plan parent that is not the stack member below, a head moved outside the controller, a changed base (an open member may sit on the trunk once every member below it landed; a landed member keeps its review base, which is never required to be the trunk), a closed member, or an open member above the highest selected one that is not an unselected packet node (`NEEDS_JUDGMENT`); an open member below the highest selected one that is not selected (`BLOCKED`: the async merge includes every open member below the requested one, so an implicitly broader prefix is never requested); an unknown trunk policy, a resolved action other than `direct_merge` or `merge_queue`, or a decided method the trunk does not allow (`BLOCKED`).

The request is one `PUT .../pulls/<n>/merge-async` for the highest selected member `n`, with `sha` its head and `bypass_rules=false`. `merge_queue` sends no merge method: the queue rules select it and the packet's method is reported as not sent. `direct_merge` sends the method decided for `n`. The server-side `sha` guard protects only `n`'s head; lower members are verified by this controller's refresh before the request and by their landing proofs after it. Before the request every open scope member's gate is renewed under the native rules (`lifecycle.evaluate(..., native_stack=True)`; a `WAITING` gate is monitored within the window) and the invoking checkout must be clean, then unchanged under the lock. Under the lock every scope and retained member is re-read and its head fetched object-only when missing, and the journal records each member's head, review base, full tree and own-slice identity (the exact `diff-tree` delta from the lowest member's single fork point with its base, or from the head of the member below, which must be a strict ancestor), each retained member's fork (the selected head) and the request as `DISPATCHING`. The request is then sent exactly once.

| Answer | Request | Run |
| --- | --- | --- |
| Accepted with a UUID echoing exactly the action, the method (`default` when none was sent), the head and `bypass_rules=false`, or an immediate `merged`/`enqueued` answer | `ACCEPTED` | follows the landings |
| 409 naming a request with exactly those options | `ACCEPTED` (adopted; not this run's mutation) | follows the landings |
| 409 naming a request with other options | `REJECTED` | `NEEDS_JUDGMENT`; that request is never adopted or replaced |
| Definite refusal (4xx, a stale head, a `failed` answer, or options the client refuses before sending) | `REJECTED` with the provider detail | `WAITING` for a stale head, otherwise `BLOCKED`; a new graph run is needed |
| Unknown outcome | `UNKNOWN` | `NEEDS_JUDGMENT` |
| An answer that does not echo the request | `UNKNOWN` | `NEEDS_JUDGMENT` |
| Not sent: less than the minimum mutation window remained, or the GitHub CLI is missing | `PLANNED` (the dispatch is undone) | `WAITING` or `BLOCKED`; resumption sends it |

The run also checks before journaling `DISPATCHING` that at least the minimum mutation window (10 s) of the monitoring window remains; otherwise it stops `WAITING` with the request still `PLANNED`. No path sends a dispatched request again, resumption included. A journal left `DISPATCHING` is reconciled as `UNKNOWN`. An `UNKNOWN` request is decided from pull request facts only: while no member has landed it is `NEEDS_JUDGMENT` (inspect the provider, then resume); landed members are proved as below.

A `REJECTED` request whose scope later lands under another actor remains `NEEDS_JUDGMENT`, not accepted or complete; inspect those provider landings without another request. A refused request whose members remain open is `BLOCKED`. The read-only preview reports the same classification.

Pull request states, not the request status, decide what landed. Each poll reads the request status when its UUID is known (a request the provider no longer reports leaves pull request facts to decide) and every scope member. `enqueued` is not a merge and stays `enqueued` after the queue lands the members; queue groups are independent and may land members at different times; a `merged` status while members are still open is provider lag. Waiting is bounded by the monitoring window, ends `WAITING` and continues on resumption. Each member reported `MERGED` is proved parent-first under the lock: its landing is reachable from the fetched trunk tip and follows the landing of the member below it, and its tree equals the clean three-way tree of its own slice (base the slice start, ours the trunk before the landing, theirs the frozen head). The trunk before the landing is the landing's first parent (a squash or merge commit, or a rebase of one commit) or, for a rebase of a member with N > 1 non-merge commits, the parent of the N-th linear first-parent commit back (`GitRepository.landing_bases`). Unrelated trunk commits between landings are allowed when that tree holds; a conflict or another tree is `NEEDS_JUDGMENT` and nothing is cleaned up. The landing, its tree and `verified` are journaled per member. A member closed without a merge, a head changed after the request, or a member landed above an open one is `NEEDS_JUDGMENT` without a replacement request. A `failed` request keeps every proved landing, journals the provider's bounded message and stops `BLOCKED`; nothing is retried or rolled back.

Once the whole scope landed, the retained members are verified as the provider left them; this controller never pushes, retargets or rewrites them. The lowest one must be open on the trunk with a new head that contains the selected member's landing and sits on `B`, the single merge base of the trunk tip and that head, with exactly the clean three-way tree (base its fork, ours `B`, theirs its frozen head) and the frozen own-slice identity over `B`: nothing missing, nothing extra. It may instead keep its frozen head when it was retargeted onto the trunk and its fork (the selected head) is already contained in the trunk tip, as after a merge landing. A higher retained member must contain the current head of the member below it: untouched when that member kept its head, otherwise rebased onto it under the same proof. A retained member not yet rebased or retargeted is provider lag (`WAITING` once the window ends); any other change is `NEEDS_JUDGMENT` before any cleanup, with the retained PR and its refs untouched. A verified retained head becomes that node's last confirmed head. Retention is proved once: after a selected node's lifecycle run id is journaled, resumption no longer checks or verifies the retained members, and a later change of one (its operator's push, a merge or a close) is reported in `retained_changes` instead of stopping acceptance or cleanup.

Then every selected node runs through `lifecycle.execute` with a `NativeLanding` context (trunk, stack number, position), which admits only a provider-`MERGED` member at that position of that stack and base: its landing is fetched and proved on the trunk, post-merge acceptance runs on a trunk checkout, and `clean` cleanup keeps every ref an open PR uses, so the retained members' branches stay. Selected members that landed before the run need no request and take the same path. A failed post-merge command is merged-but-incomplete; resumption keeps the journaled landings and never sends another request. A completed native run re-verifies as lifecycle no-ops without any write, and `--until pr` and `--dry-run` write nothing.

### Graph endpoints

| Endpoint | Finishes when |
| --- | --- |
| `pr` | Observation only; nothing is captured, promoted, retargeted, merged or deleted |
| `renewed` | Every selected existing manual PR is source-renewed at its verified head/base; no landing, post-merge acceptance or deletion |
| `merged` | Every selected node landed and passed its post-merge acceptance; no feature branch is deleted |
| `clean` | `merged`, plus each node's proof-based lifecycle cleanup |

Lifecycle cleanup retains any ref an open PR uses as head or base, selected or not, in the base repository or a fork, with the reason `an open PR uses this namespace/ref as head or base`. A landed node whose acceptance passed and whose only failed required cleanup targets carry that reason is deferred; once its dependents are landed or retargeted, the same receipt and endpoint resume its cleanup without another merge. A dependent that stays open, such as an unselected sibling or child, leaves the run `BLOCKED` with the exact `dependents` and the next action to land or retarget them and resume for cleanup only. A failed post-merge command or any other incomplete required cleanup is merged-but-incomplete: `BLOCKED` with the confirmed merges preserved, never `COMPLETE`. Resuming a completed graph run with its saved endpoint, unchanged controller sources and no packet of another identity re-verifies that every selected node is still `MERGED` at its journaled head and that its receipt completes as an unchanged lifecycle no-op, writing no journal; a mismatch is `BLOCKED`. A refreshed packet of the same topology continues the run through the lifecycle instead.

### Graph output

Execution returns `schema_version`, `run_id`, `status`, `target` (`kind: "stack"`, `host`, `repository`, `trunk`, `endpoint`, `selected`), `nodes`, `observed_revisions.trunk`, `confirmed_commits` (`pr`, `ref`, `old`, `new` of every confirmed rewrite push), `confirmed_prs`, `confirmed_merges`, `verification`, `cleanup` (`removed`, `retained`, `failed`, each row naming its `pr`), `dependents` (`landed`, `pr`, `url`, `namespace`, `ref`), `retained_local`, `retained_changes` (`pr`, `reason`), `findings`, `pending_intents`, `node_result` (the stopped node's lifecycle result), `usable_checkout`, `blocker`, `next_action`, `diagnostic`, `mutation_attempted`, `mutation_performed` and `cancelled`. Each `nodes` row holds `pr`, `role` (`selected` or `retained`), `parent`, `state`, `run_id`, `head`, `base`, `status`, `blocker`, `landing`, `promotion` and `cleanup`. Confirmed merges and every other confirmed fact are reported whatever the final status.

`--dry-run` returns `schema_version`, `run_id`, `status: PLANNED`, `target`, `observed_revisions.trunk`, `local_snapshot`, `nodes` (`pr`, `role`, `parent`, `state`, `membership`, `head`, `base`, `landing`), `actions`, `blockers`, `retained_changes`, `confirmed_prs`, `confirmed_merges`, an empty `cleanup`, `next_action` and `mutation_performed: false`. Actions are `reconcile` (a resumed run's pending intent with its read-only outcome), `capture` (with the fork boundary check), `promote` (with its `proof`), `retarget`, `land` (with the merge method and, for a node ready now, the current gate decision), `verify-landing` for landed nodes, and `cleanup` under `clean`; `pr` lists no action.

A native selection adds `native` to both results. Execution reports `stack`, `trunk`, `selected`, `scope`, `retained`, `merge_action`, `merge_method`, `method_sent`, `packet_merge_method`, `method_note` (for a queue: the packet's method was not sent), `guard` (the server guards only the selected head), the journaled `request`, `request_read`, `landings` (`pr`, `position`, `head`, `landing`, `landed_tree`, `verified`), `retained_verification` and the last `gates`. `--dry-run` lists `native-merge` (`prefix`, `expected_head` and the request options), or `reconcile-request` for a `DISPATCHING`/`UNKNOWN` request (with its read-only outcome) or `await-landings` for an accepted one, then `verify-landing` for every selected node, `verify-retained` for every retained member and `cleanup` under `clean`; its `native` block adds each open scope member's gate and `retained_preview` (head, base, fork, the read-only fork proof and why the member is protected).

### Graph limits

- GitHub has no documented atomic head/base guard for a retarget; the pre- and post-reads narrow the race only.
- Promotion is plumbing-only and never signs: configured `commit.gpgSign` or a signed slice commit is `NEEDS_JUDGMENT` with nothing rewritten, and signing is never disabled. Provider-side signature requirements are not observable here; a remote that refuses the unsigned promoted head while still holding `C` leaves the run `BLOCKED`.
- Promoted commits get the repository's committer identity and a new timestamp, and the replay runs no hook. Pushes still run the repository's hooks.
- The execution proof uses Git's merge machinery, so repository merge configuration and `.gitattributes` affect the expected tree; the dry-run preview runs without them and does not replay per commit.
- A slice holds at most 256 commits. A fork is never fetched by object id.
- The lock coordinates cooperating invocations of this workflow, not other Git processes, editors or remote actors.
- Regressions use real temporary Git repositories with local bare remotes and a stateful provider fixture; they are not vendor proof of every provider configuration.
- Native execution relies on provider behaviour observed on GitHub (the request merges the open prefix; `sha` guards only the selected head; a landed member keeps its review base; `enqueued` stays `enqueued` after the members land; queue groups land independently; the provider rebases and retargets the retained member). GitHub documents no atomic or single-group guarantee for a stack merge and none is claimed. Regressions model these facts with a stateful fixture.
- Every open member above a native selection must be an unselected packet node, so its retention can be bound before the request.
- A rebase landing is proved only as one linear replay of the member's own commits directly on the trunk; a landing with other commits interleaved needs judgment. Frozen member heads are fetched objects without a ref, so `git gc` may prune one after its pruning grace period during a long wait; a later proof then stops `BLOCKED` on the missing object.
- The controller code identity covers `native_stack.py` with the other controller sources: an edit to it alone makes every saved single-PR receipt and every manual or native graph journal `NEEDS_JUDGMENT` on resumption until a refreshed policy or `--stack-plan` packet is supplied.

## Error handling

Resolve ordinary change-owned failures without weakening acceptance. Unknown CI ownership, grouping, scope or applicability is a bounded decision, not automatic GREEN. Permission/inherited/protection failures stay blockers. Never solicit reviewer bots, bypass protections, rewrite unrelated user work, or infer release version/changelog/tag/publication authority from ordinary shipping.
