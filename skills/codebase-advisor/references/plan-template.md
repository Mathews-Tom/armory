# Handoff Plan Template

Every plan is written for an executor model with zero context from the advisor session. It may be smaller, cheaper, and worse at inference. The plan must remove judgment calls that can be resolved by the advisor.

A good plan has three properties:

1. **Self-contained context** — paths, excerpts, conventions, commands, and assumptions are in the file.
2. **Verification gates** — each step has a command and expected result.
3. **Hard boundaries** — in-scope files, out-of-scope files, and STOP conditions are explicit.

File naming: `plans/NNN-short-slug.md`, numbered in recommended execution order.

## Plan File Template

```markdown
# Plan NNN: <Imperative title — what will be true after this plan>

> **Executor instructions**: Follow this plan step by step. Run every verification command and confirm the expected result before moving to the next step. If anything in "STOP conditions" occurs, stop and report — do not improvise. When done, update the status row for this plan in `plans/README.md` unless a reviewer dispatched you and told you they maintain the index.
>
> **Drift check (run first)**: `git diff --stat <planned-at SHA>..HEAD -- <in-scope paths>`
> If any in-scope file changed since this plan was written, compare the "Current state" excerpts against live code before proceeding; on mismatch, stop and report.

## Status

- **Priority**: P1 | P2 | P3
- **Effort**: S | M | L
- **Risk**: LOW | MED | HIGH
- **Depends on**: plans/NNN-*.md or "none"
- **Category**: bug | security | perf | tests | tech-debt | migration | dx | docs | direction
- **Planned at**: commit `<short SHA>`, <YYYY-MM-DD>
- **Issue**: <GitHub issue URL — include only when published via `--issues`>

## Why this matters

2-5 sentences. Name the concrete problem, current cost, and what improves when this lands.

## Current state

- Relevant files and their roles:
  - `path/file.ext` — role; issue location at lines X-Y.
- Current code excerpts with `file:line` markers. Keep excerpts short but sufficient for drift checks.
- Repo conventions to follow, with an exemplar file and lines.
- Relevant decisions/vocabulary from ADRs, `CONTEXT.md`, `DESIGN.md`, or `PRODUCT.md`, quoted with line references when applicable.

## Commands you will need

| Purpose | Command | Expected on success |
|---|---|---|
| Install | `<command>` | exit 0 |
| Typecheck | `<command>` | exit 0, no errors |
| Tests | `<command>` | all pass |
| Lint | `<command>` | exit 0 |

Use exact commands observed during recon. Do not guess.

## Suggested executor toolkit

Include only when relevant:

- Skills/tools the executor should invoke.
- Reference docs worth reading before starting.

## Scope

**In scope** — the only files to modify:

- `path/file.ext`
- `path/file.test.ext`

**Out of scope** — do not touch even if related:

- `path/legacy.ext` — reason.
- Public API shape — clients depend on it.

## Git workflow

- Branch: `<repo convention or advisor/NNN-slug>`
- Commit style: `<repo convention with example>`
- Do not push, merge, or open a PR unless the operator explicitly instructed it.

## Steps

### Step 1: <imperative title>

Precise instructions. Name files, symbols, target behavior, and constraints. Include target code shape only when it is load-bearing.

**Verify**: `<command>` → `<expected result>`

### Step 2: <imperative title>

Precise instructions.

**Verify**: `<command>` → `<expected result>`

## Test plan

- New tests to write, file location, and exact cases.
- Existing test to use as structural pattern.
- Verification command and expected result.

## Done criteria

All must hold:

- [ ] `<typecheck command>` exits 0.
- [ ] `<test command>` exits 0, including named new tests.
- [ ] `<lint command>` exits 0.
- [ ] Old pattern is gone: `<search command>` returns no matches, when applicable.
- [ ] No files outside the in-scope list changed.
- [ ] `plans/README.md` status row updated, unless reviewer owns the index.

## STOP conditions

Stop and report back if:

- Current-state excerpts do not match live code.
- A step's verification fails twice after a focused fix attempt.
- The fix requires touching out-of-scope files.
- A key assumption named in this plan is false.
- A sensitive value is discovered; report location/type only and do not copy the value.

## Maintenance notes

- Future code paths that must use the new pattern.
- What reviewers should scrutinize.
- Follow-ups intentionally deferred out of this plan and why.
```

## Index Template: `plans/README.md`

```markdown
# Implementation Plans

Generated by `codebase-advisor` on <date>. Execute in the order below unless dependencies say otherwise. Each executor must read the plan fully, honor STOP conditions, and update status when done.

## Execution order & status

| Plan | Title | Priority | Effort | Depends on | Status |
|---|---|---|---|---|---|
| 001 | ... | P1 | S | — | TODO |
| 002 | ... | P1 | M | 001 | TODO |

Status values: TODO | IN PROGRESS | DONE | BLOCKED (reason) | REJECTED (rationale)

## Dependency notes

- 002 requires 001 because <reason>.

## Findings considered and rejected

- <finding>: not worth doing because <one-line rationale>.
```

## Quality Bar

Before finishing each plan, check:

- A fresh executor can act using only the plan file and repo.
- Every verification is a command with expected result.
- Every step names exact files and symbols.
- STOP conditions are specific, not boilerplate.
- Scope boundaries prevent opportunistic refactors.
- No secret values appear.
- Planned-at SHA and drift check paths match scope.
- The human reviewer can understand intent from "Why this matters" and done criteria alone.
